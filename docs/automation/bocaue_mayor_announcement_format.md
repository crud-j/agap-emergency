# Bocaue Mayor's Office — Automated Announcement Format
## Mobile App Content Standard

**Purpose:** Define a consistent, accessible, and approval-controlled format for announcements published through the mobile app for the Municipality of Bocaue, Bulacan.

**Status:** Proposed system template. This document is an implementation recommendation, not a claim that it reproduces the mayor's existing Facebook templates or an officially approved municipal communications policy.

---

## 1. Core principles

Every announcement should be:

- **Accurate:** Use only details confirmed by the responsible office.
- **Clear:** Put the main message and any required action first.
- **Local:** Name the affected barangays, facilities, roads, or services in Bocaue.
- **Time-specific:** Include dates, times, and effective periods when relevant.
- **Accessible:** Use plain Filipino or English, short paragraphs, and readable graphics.
- **Traceable:** Record the issuing office, approver, publication time, and any correction.
- **Approval-controlled:** Generated text must remain a draft until an authorized person approves it.

Do not automatically publish AI-generated or form-generated announcements without human review. Never invent dates, affected areas, causes, instructions, contact details, or official decisions.

## 2. Supported announcement categories

Use a category to select the right template and required fields.

| Category | Example use | Required information |
|---|---|---|
| Public advisory | Service interruption, public reminder | Subject, details, effective date/time, affected area, action |
| Emergency / safety | Severe weather, flooding, fire, other hazards | Verified situation, affected area, time, safety instructions, official source |
| Class suspension | Suspension of classes | Authorized decision, covered date, affected schools/levels, scope |
| Traffic / road advisory | Road closure, rerouting, traffic changes | Road/location, start/end time, affected users, alternative route if confirmed |
| Municipal service | Health mission, document processing, assistance | Service, eligibility, date/time, venue, requirements, contact |
| Event / community activity | Municipal event or consultation | Event, date/time, venue, audience, registration if applicable |
| Project update | Infrastructure or public works progress | Project, location, verified status, schedule/impact, responsible office |
| Official statement | Clarification or response | Issue addressed, verified facts, authorized position, contact/source |
| Recognition / celebration | Achievement, greeting, tribute | Occasion/person/community, accurate details, approved message |

## 3. Standard announcement data model

Store announcement content as structured fields rather than one long text box.

| Field | Required? | Notes |
|---|---|---|
| `announcement_id` | Yes | Unique ID generated by the system |
| `title` | Yes | Short, specific headline |
| `category` | Yes | One category from Section 2 |
| `priority` | Yes | `routine`, `important`, or `urgent`; reserve urgent for time-critical matters |
| `language` | Yes | `fil`, `en`, or `fil-en` |
| `summary` | Yes | One- or two-sentence overview |
| `body` | Yes | Full announcement text |
| `action_required` | When applicable | What residents should do |
| `start_at` | When applicable | Local effective start date/time |
| `end_at` | When applicable | Local end date/time, if known |
| `affected_locations` | When applicable | Specific barangays, streets, facilities, or municipality-wide scope |
| `audience` | When applicable | Residents, commuters, parents, service applicants, etc. |
| `venue` | When applicable | Exact venue, if relevant |
| `requirements` | When applicable | Documents, eligibility, fees (only if verified) |
| `contact_office` | When applicable | Responsible office and verified contact channel |
| `source_reference` | Yes for factual advisories | Official memo, order, responsible office, or verified source |
| `issuing_office` | Yes | Office accountable for the information |
| `prepared_by` | Yes internally | Staff account or role |
| `approved_by` | Before publishing | Authorized approver and approval timestamp |
| `published_at` | System-generated | Publication timestamp |
| `status` | Yes | `draft`, `for_review`, `approved`, `scheduled`, `published`, `corrected`, `cancelled`, `archived` |
| `correction_note` | If corrected | What changed and when |
| `attachments` | Optional | Approved poster, map, document, or photo |
| `channels` | Yes | Mobile app, push notification, and/or approved social channels |

Use the Asia/Manila time zone for displayed local dates and times. Store timestamps consistently (preferably ISO 8601 with an explicit offset or UTC plus a configured display time zone).


## 5. English template

```text
[SHORT, SPECIFIC HEADLINE]

PUBLIC ADVISORY

The [issuing office] informs the public that [main announcement in one clear sentence].

Date: [Day, date]
Time: [Time or “Not applicable”]
Location / affected areas: [Exact location or barangays]
Who is affected: [Audience or scope, if applicable]

WHAT YOU NEED TO DO
[Clear, verified instructions. Remove this section if no action is needed.]

MORE INFORMATION
For questions, contact [responsible office] through [verified contact channel].

Issued by: [Office]
Reference: [Official memo / order / source, where applicable]
```

## 6. Bilingual template

For announcements intended for broad public reach, the app may offer Filipino first and English second. Keep both versions factually equivalent.

```text
[HEADLINE / PAMAGAT]

PAALALA SA MGA BOCAUEÑO

[Filipino announcement, including dates, affected locations, and instructions.]

PUBLIC ADVISORY

[Equivalent English announcement with the same dates, locations, and instructions.]

Inilabas ng / Issued by: [Office]
Sanggunian / Reference: [Verified official source]
```

Do not publish a translation until dates, locations, numbers, and instructions have been checked against the approved source.

## 7. Category-specific templates

### A. Emergency or safety advisory

```text
[URGENT SAFETY HEADLINE]

ABISO SA KALIGTASAN

Batay sa impormasyong beripikado ng [responsible office/source], [confirmed situation] sa [affected location] simula [date/time].

PINAG-IINGATAN / MGA DAPAT GAWIN
- [Verified safety instruction]
- [Verified evacuation or assistance instruction, if officially directed]
- [Official hotline or contact, if confirmed]

Apektadong lugar: [Specific locations]
Huling beripikasyon: [Date/time]
Inilabas ng: [Authorized office]
Sanggunian: [Official source]
```

Only use “URGENT” when warranted. Do not state that an evacuation, closure, or emergency measure has been ordered unless the competent authority has confirmed it. Keep emergency instructions consistent with the responsible emergency-management office.

### B. Class suspension

```text
ANUNSYO: SUSPENSIYON NG KLASE

Ipinababatid ng [authorized issuing authority] na suspendido ang klase sa [covered schools / levels / area] sa [date], alinsunod sa [verified order or official basis].

Saklaw: [Public/private schools and grade levels, exactly as authorized]
Petsa ng bisa: [Date and any specified time]
Iba pang detalye: [Verified details]

Sanggunian: [Official order / source]
Inilabas ng: [Authorized office]
```

The system must not infer a suspension from a weather forecast. Require the authorized decision and exact scope before publishing.

### C. Road closure or traffic advisory

```text
ABISO SA TRAPIKO

Magkakaroon ng [road closure / rerouting / traffic adjustment] sa [exact road or location] sa [date], mula [start time] hanggang [end time], dahil sa [confirmed reason, if approved for release].

Apektadong lugar: [Roads / intersections]
Mga motorista: [Verified instructions]
Alternatibong ruta: [Only if confirmed by the responsible office]
Inilabas ng: [Office]
Sanggunian / contact: [Verified source]
```

### D. Municipal service or assistance program

```text
SERBISYONG BAYAN: [PROGRAM NAME]

Inaanyayahan ang [eligible residents] na lumahok / mag-avail ng [service].

Petsa: [Date]
Oras: [Time]
Lugar: [Venue]
Mga kwalipikado: [Verified eligibility]
Mga kailangang dalhin: [Verified requirements]
Paraan ng paglahok: [Registration / walk-in / appointment, as confirmed]
Mga tanong: [Responsible office and verified contact]

Paalala: [Verified limitations or conditions, if any.]
```

Never invent eligibility, fees, benefit amounts, quotas, or promises of approval.

### E. Project or service update

```text
UPDATE SA BOCAUE: [PROJECT / SERVICE]

Ibinabahagi ng [responsible office] ang beripikadong update tungkol sa [project/service] sa [location].

Kasalukuyang kalagayan: [Confirmed status]
Susunod na hakbang / iskedyul: [Confirmed information]
Epekto sa mga residente: [Confirmed impact or none known]
Mga tanong: [Responsible office/contact]

Sanggunian: [Official project record / office]
```

Describe progress factually. Do not label a project “completed” or “on schedule” unless the responsible office confirms it.

### F. Event or community activity

```text
INAANYAYAHAN ANG MGA BOCAUEÑO: [EVENT NAME]

Makilahok sa [brief, verified event description].

Petsa: [Date]
Oras: [Time]
Lugar: [Venue]
Sino ang maaaring dumalo: [Audience]
Pagpaparehistro / requirements: [If applicable]
Karagdagang impormasyon: [Office/contact]
```

### G. Correction or cancellation

```text
PAGWAWASTO / UPDATE SA NAUNANG ANUNSYO

May pagwawasto / pagbabago sa naunang anunsyo na inilabas noong [date/time] tungkol sa [subject].

Naunang impormasyon: [Brief, factual description]
Tamang / bagong impormasyon: [Corrected information]
Epektibo mula: [Date/time, if applicable]

Paumanhin sa anumang kalituhan. Para sa beripikasyon, makipag-ugnayan sa [responsible office].

Inilabas ng: [Office]
```

Keep the original record in the audit trail. Do not silently overwrite a material correction.

## 8. Automated title and push-notification rules

### Title formula

Use:

`[CATEGORY]: [SPECIFIC SUBJECT] — [LOCATION, if needed]`

Examples (illustrative only; not actual Bocaue advisories):

- `PAALALA: Pagbabago sa Oras ng Serbisyo`
- `ABISO SA TRAPIKO: Pansamantalang Pagsasara ng [Kalsada]`
- `SERBISYONG BAYAN: [Pangalan ng Programa]`
- `UPDATE: [Pangalan ng Proyekto]`

### Push notification

Push notifications should be brief and direct. The full announcement should open inside the app.

```text
[SHORT TITLE]
[What residents need to know]. Tingnan ang buong detalye sa app.
```

Rules:
- Aim for a title of roughly 35–60 characters and a body of roughly 80–140 characters; treat these as editorial targets, not platform limits.
- Include the date or affected area when it changes what a resident needs to do.
- Do not put all the details in the push message.
- Avoid excessive capitalization, alarmist language, unexplained abbreviations, and multiple emojis.
- For urgent announcements, follow the municipality's approved emergency communications protocol.

## 9. Suggested mobile-app layout

1. **Category label:** Public Advisory, Safety, Traffic, Service, Event, Update.
2. **Priority label:** Routine, Important, or Urgent.
3. **Headline:** Clear and specific.
4. **Summary:** One or two sentences.
5. **Key details:** Date, time, affected area, venue, and audience as relevant.
6. **Required action:** A short checklist or instruction section, only when needed.
7. **Attachments:** Approved poster, map, official document, or relevant photo.
8. **Issuing office and source:** Show who is responsible and, when appropriate, link to the source.
9. **Published / updated timestamp:** Display local time and date.
10. **Correction status:** Prominently mark corrected, cancelled, or superseded announcements.

Support screen readers, sufficient color contrast, scalable text, descriptive image alt text, and links that clearly state their destination. Never rely on color alone to communicate urgency.

## 10. Recommended approval workflow

```text
Staff creates announcement
        ↓
System checks required fields
        ↓
Responsible office verifies facts and source
        ↓
Authorized approver reviews wording and scope
        ↓
Approve / Return for edits / Reject
        ↓
Publish or schedule in the mobile app
        ↓
Send push notification if selected and authorized
        ↓
Monitor, update, correct, expire, or archive
```

Recommended safeguards:

- Role-based permissions for authors, reviewers, approvers, and publishers.
- Separate the person who drafts a notice from the final approver where practical.
- Require extra authorization for emergencies, class suspensions, evacuation instructions, and municipality-wide notices.
- Save the approved version, approver, timestamps, source documents, and publication history.
- Allow authorized staff to unpublish or mark a notice as cancelled, without deleting the audit trail.
- Expire time-limited announcements automatically only after their expiry behavior has been approved; preserve them in the archive.
- Provide a preview of the app card, full announcement, and push notification before approval.
- Never represent a draft or unapproved statement as an official announcement from the mayor.

## 11. Suggested status and priority definitions

### Workflow status

| Status | Meaning |
|---|---|
| `draft` | Being prepared; not visible to the public |
| `for_review` | Submitted for verification or approval |
| `changes_requested` | Returned to the author for edits |
| `approved` | Authorized for publication |
| `scheduled` | Approved and set to publish later |
| `published` | Visible to the intended audience |
| `corrected` | A corrected version has been issued |
| `cancelled` | Officially withdrawn or cancelled |
| `archived` | No longer active; retained for reference |

### Priority

| Priority | Use |
|---|---|
| `routine` | General information, events, regular services |
| `important` | Significant changes or time-sensitive services |
| `urgent` | Immediate action may be needed to protect safety or respond to a critical disruption |

Priority must reflect the actual situation, not a desire to increase views or engagement.

```json
  "body": "[Approved full announcement]",
  "action_required": "[Verified action, or null]",
  "start_at": null,
  "end_at": null,
  "affected_locations": [],
  "audience": [],
  "venue": null,
  "requirements": [],
  "contact_office": {
    "name": "[Verified office]",
    "contact": "[Verified official channel]"
  },
  "source_reference": "[Official memo or source record]",
  "issuing_office": "[Responsible office]",
  "prepared_by": "[Staff user ID]",
  "approved_by": null,
  "approved_at": null,
  "published_at": null,
  "status": "draft",
  "correction_note": null,
  "attachments": [],
  "channels": ["mobile_app", "push_notification"]
}
```

Implementation notes:

- Validate `category`, `priority`, `language`, and `status` against server-side enumerations.
- Enforce authorization on the server; hiding an Approve button in the UI is not sufficient.
- Do not allow `published` status unless approval requirements are satisfied.
- Store source documents and contact details with appropriate access controls.
- Escape or sanitize rich text before rendering it.
- Do not store sensitive personal information in public announcement fields.
- If social media cross-posting is later added, use authorized accounts and supported platform integrations; do not assume a mobile-app post automatically publishes to Facebook.
